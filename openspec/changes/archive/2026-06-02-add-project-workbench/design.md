## Context

当前仓库已经具备稳定的认证流程，以及一个基于 site profile 和 highlight 数据的简单认证后首页。这套基线足够证明技术栈和工程能力，但还不能支撑用户真正的日常使用目标，也就是把它当作一个轻量的个人知识工作台，用来沉淀项目想法和持续推进中的项目。

已经确认的产品方向是“轻量项目工作台”，包含两个核心层次：

- 一个强调状态总览与项目卡片的 dashboard 首页
- 一个承载当前目标、下一步动作与更新记录的项目详情页

同时，用户希望在正式编码前，先通过 Figma 重构登录页与认证后首页，让整个产品从“工程演示页”转向“真的可以日常使用的工具”。

## Goals / Non-Goals

**Goals:**

- 让认证后的首页真正适合每日查看和记录项目推进状态。
- 保持项目创建门槛足够低，第一版只强制要求项目名、状态和下一步动作。
- 提供独立的项目详情工作区，用于承载项目上下文与持续更新记录。
- 让登录页与新的“个人项目工作台”产品定位保持一致。
- 在仍然适合当前仓库的地方，尽量复用现有认证与渲染模式。

**Non-Goals:**

- 本次变更不构建完整知识图谱、标签系统或 AI 优先的知识助手。
- 不引入文件上传、附件管理或复杂协同编辑能力。
- 不替换当前认证模型、Redis session 架构或部署基线。
- 在项目工作台能力真正落地前，不在本次设计中提前定死现有 highlight 流程的迁移或归档策略。

## Decisions

- 引入一个新的一级领域对象 `Project`，而不是直接在现有 `Highlight` 模型上强行演化。
  - 复用 `Highlight` 确实可以减少短期 schema 工作量，但会让领域语义长期失真，也会让未来的 UI 和 API 逐渐变得难以理解。
  - 独立的项目模型可以保持产品语言清晰，避免把工作台永久绑定在一个过渡性质的基线对象上。

- 将项目归属直接建模到认证用户或用户级工作区边界上，而不是继续沿用首页文案对象去承载项目。
  - 如果继续把 `SiteProfile` 当作主要容器，会让核心数据模型始终带着“个人站首页”的旧产品语义。
  - 直接归属到用户，会让项目查询、筛选和权限边界更清晰，也更符合工作台的长期方向。

- 第一版创建流程刻意保持最小：`name + status + nextAction`。
  - 想要形成日常使用习惯，最快的路径就是降低记录阻力。
  - 背景、当前目标、参考资料这类更丰富的信息，应该在项目创建之后放到详情页里补充。

- 将认证后的首页重构为工作台 Dashboard，并明确三块主区域：
  - `想法中 / 进行中 / 已暂停 / 已完成` 四种状态卡片
  - 支持筛选的项目卡片列表
  - 最近更新区块

- 增加独立的项目详情路由，而不是把所有字段都塞进 dashboard 卡片中。
  - dashboard 应该保持适合扫读和快速判断。
  - 详情页才适合承载当前目标、更新记录和未来的参考资料等更深层上下文。

- 在保留现有认证 API 和 redirect 逻辑的前提下，把登录页重构为真正的产品入口页。
  - 这样可以在不承担高风险认证重写成本的情况下，让 UI 更清楚地传达工作台价值。

- 在实现前先产出登录页和工作台首页的 Figma 设计稿。
  - 这次重构影响的不只是视觉样式，更重要的是信息层级与产品定位。
  - 先在 Figma 中确认页面结构，会比写完代码再回头补设计更稳。

## Risks / Trade-offs

- [Risk] 新增独立项目模型会比复用 highlights 带来更大的 schema 和 UI 范围。→ Mitigation: 第一版先保持最小数据契约，把高级字段延后到 dashboard 流程稳定之后。
- [Risk] 在规划阶段保留 highlight 流程，会让仓库在一段时间内存在叙事重叠。→ Mitigation: 把 highlight 的迁移或下线作为后续明确决策，而不是隐含在第一版 spec 里。
- [Risk] 如果第一版塞入过多管理功能，dashboard 容易变乱。→ Mitigation: V1 严格限制在状态总览、项目列表、项目详情和更新记录。
- [Risk] 如果 Figma 设计范围失控，会拖慢实现节奏。→ Mitigation: 第一轮 Figma 仅覆盖登录页和主工作台首页。

## Migration Plan

1. 先基于已确认的产品结构完成登录页和 dashboard 的 Figma 设计；如果 Figma 受限，则在同一个 change 内直接推进登录页和首页的 UI 重构实现。
2. 在现有认证体系之上引入新的项目模型与项目 API。
3. 用项目工作台 dashboard 替换当前以 highlights 为中心的首页。
4. 增加项目详情页和更新记录能力。
5. 等工作台稳定后，再决定现有 highlight 流程是移除、迁移还是保留为独立入口。

Rollback strategy:

- 将首页和登录页恢复为当前实现。
- 如果工作台在正式采用前回滚，则保留新增项目表但不启用对应入口。
